# 新建三次确认：准备怎么收

对照你刚才那次，以及 [增删改审手测集](biz-write-eval.md)、[增删改审交互](biz-write-interaction-audit.md)。

新建、改行、删除、过审是同一条确认逻辑。根因已写在 [连弹确认根因](write-confirm-root-cause.md)。下面三刀已按契约进代码，没有另起一套。现网闸与 BFF 已换上。**还没**在现网点过账，手验仍按文末那一步。

## 收成什么样才算好

人说一句新建、点一次「确认过账」：

1. 只出现 **一张** 确认。
2. 点下去：立刻成功或失败；成功则库里多这一行，抽屉关掉。
3. **不得**再弹确认。左边去现查，也只是查，不再开「确认过账」。
4. 若有人误点第二下，才可以报「这张预览已经用过」——正常路径里不该见到这句。

## 你那三次分别是什么（先查，再对号入座）

不猜死哪一张。用最近这次会话的 jsonl + `biz_write_audit` + pending，把三次弹窗对上 `preview_id`：

| 你看见的 | 要钉死的 |
|---|---|
| 第一张，你点了 | 哪个令牌、BFF 是否 200、库里有没有行 |
| 马上第二张，点了报「已经用过」 | 还是 **同一张已 USED 的令牌** 被重新打开，还是 **第二枚** 令牌 |
| 左边现查完第三张 | 秘书 wrote 之后的现查又落成新建，还是 hydrate 把旧 pending 又画成可确认 |

三种都对得上，再改。改之前只读。

## 准备怎么改（按人看见的结果，不另起一套）

1. **写成功就收令牌。** 人点确认且闸写成功：这枚 `preview_id` 标记 USED，关抽屉，dismiss。hydrate / SSE **不得**再拿这枚令牌开「确认过账」。
2. **同一 opening 不得留下第二张能确认的死令牌。** 一次确认只对应这一笔新建；merge 出来的旧令牌一起作废。
3. **过账后的现查就是现查。** 秘书「库里已改上」之后，工具参数是现查就不得再落成新建写预览，也就不会出第三张确认。
4. **不拆 round-end。** 预览一成功就刷表会乱，那条继续停着。

不写死工单、不写死「确认过账」文案。词表+图+schema 收槽；抽屉只认「未使用的写预览令牌」。

不把 hall / round / lastEmitted / 前端当四套同功能删三套。清的是它们各自冒充待确认；活留下当投影。见 [连弹确认根因](write-confirm-root-cause.md)。

## 你怎么验

新开会话，再说一句新建（带处理人也可以）。只应有一张确认。点一次后：抽屉关、左边现查不再弹确认。若再弹，停在那张，把图给我。
