## 为什么页面还停在采购订单

页面在 5174，事件流走 Vite 再转到 4318。新 BFF 63367 在听 4318，Chrome 有直连（左边跟话的那路），**Vite 的 80 条转到 4318 的连接，一条都没接到 63367。**

| 对端 | 条数 | 状态 |
|---|---|---|
| 已死进程（`:53347`、`:81661`、`:90180` 等） | 73 | 对端 `FIN_WAIT_1`，Vite 这边仍是 `ESTABLISHED`，接收队列堆着读不完的旧数据 |
| 旧 BFF **20250**（9 月 23 日起） | 6 | 还活着，接收队列同样堆着 |
| 旧 BFF **14216** | 1 | 同上 |
| 新 BFF **63367** | 0 | watch 这下推送的订户不在这里 |

旧进程被杀掉之后，Vite 没把这些连接判死，浏览器的 `EventSource` 也就没有 `onerror`，不会重连，也不会改去轮询 `/api/v1/events/recent`。63367 写进 outbox、推给自己的订户；挂在死连接上的那一页收不到 `evt_0mugh9t4a_000000002`。

所以落地改的「查到就上台、推送带上表面编号」在服务器上这一问是生效的。没生效的是：重启 BFF 之后，已经开着的页面还吃着旧连接，新推送进不去。
