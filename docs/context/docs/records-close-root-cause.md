## 一句话

工作台把「闸已经查对的那一次」和「人看见的 / 模型下一步打的」拆成了两套。插件没有这套拆分，所以 10 条过。不是 overlay 把数算错，也不是词表里没有费用报销。

## 插件为什么过

```
一句话 → DSH → lan-assist 打一次 preview → 人看会话里那一次结果
```

没有第二张表。没有 BFF 再写 pending。没有取消回目录。人看见对的预览就停，最后一枪空表不会盖掉已经对的那次。

## 工作台实际多了什么

```
一句话
  ├─ 左 AI → lan-assist preview/write → /state.pendingSheet
  ├─ BFF：1s 轮询 / GET pending-sheet / POST /preview  再写 pending
  ├─ 右表 apply：空表拒绝、按住旧 kind、取消回目录
  └─ 模型看见过审没出令牌 / 右表空了 → 再打 catalog 里另一个可预览 kind
```

三路写 pending，一路画表。左栏可以已经是 97 条费用报销，右表画出报销单 0 或客户 20。

出处：[对齐根因](records-align-root-cause.md) §2。

## 上游：谁有资格当 kind

决策 15：对象 = 已连接系统的表；词表口语 = 别名；图 = 表和表的关系。

现网反了。`kindsFromGraphNodes` 从图谱 `skos:Concept` 出 kind，不是从连接器 collection 出 kind。没有对应业务表的概念也能进 catalog，也能 preview。闸把 catalog 里任意 kind 当真表打。

leftover 只认「长名以短名结尾」。费用报销不以报销单结尾，两个并列概念收不回去。工单 vs 生产工单能被 leftover 碰到，报销单 vs 费用报销碰不到。所以补 leftover 救不了第 5 条。

## 原先三问（已钉死，不再当印证清单）

出处：2026-09-17 [词表范围](../internal/vocab-graph-scope.md)、[词表补齐](../internal/vocab-complete.md)、BG [第 5 条轨迹](../internal/verify-records-close-bg.json) `aiDelta`、Z `1358425` 取消路径。

### 1. 报销单怎么进的图

不是当前连接器那张报销表生成出来的。

- NocoBase 报销业务表是 **费用报销**（`biz_expenses`）。现网现查到 97 条待审，有行。
- **报销单** 在 2026-09-17 就已经是图谱里一个独立 `skos:Concept`：`can` 现查/过审，字段 `expenseNo` / 单号 / 状态，`resource` 记成「(in graph)」，**不是** `biz_*` 表茎。catalog 按它当可预览对象。行数 0。
- 词表补齐只给**已有 resource** 的概念补 `改行`/`删除`，没有新建报销单。连接器生成会从 collection 出「费用报销」，不会再摊一张没有表的「报销单」。
- 所以报销单是图谱里另挂的概念（口语/手补/旧生成留下的并列节点），不是费用报销的别名槽。图上两节点并列，leftover 收不回去。

具体哪一次 upsert 的 `source` 字段不再追。契约不依赖这个名字：没有业务表就不能当 preview/写目标；口语短名只能当别名。

### 2. 费用报销过审为什么先失败

不是库里没待审。BG 第 5 条左栏轨迹按时间是：

1. 第一枪 `biz_preview · 过审`：闸把「待审报销**单都**过一下」吃偏（模型原话：misparsed「单都」）。
2. 两枪 `现查`：锁定 **97** 条待审（成功）。横幅后来有「费用报销 · 过审」。
3. 再打批量 `过审`：闸回报「一次最多 100 条，清单以预览时服务器…」之后模型写「The gate is having trouble」，**没有 `preview_id`**。
4. 模型自己改口：「Also try kind 报销单 as alias」→「改用报销单型」。最后 pending 是 **报销单 · 过审 · 0 行 · `preview_id` 空**。右表 chip 报销单、footer 0。

触发是：**过审两次没出令牌**（先解析偏，再批量过审卡住），模型把 catalog 里另一个可预览 kind 当别名再打。工作台把这最后一枪空表 apply 上去。

插件里人看见 97 条或第一次过审预览就停。没有右表把最后一枪 0 行盖掉。

### 3. 取消为什么倒客户目录

和短名不是同一条代码。

- Z `1358425` 已经规定：`dismissPreviewDrawer` 走 `displayBeforeWriteRef`，不走 `restoreRecordsList`，也不再 `bizPreview` 拉全表。当时取消 1 行回款能留下。
- BG 现网取消后是 **客户目录第 1 页约 20 行，首行 `CUST2056`**，不是取消前那张 `CUST2058` 改行预览。`CUST2056` 是成交客户，是目录页开头，不是这次命中。
- 第 4 条过程里还打过「客户名称含恒通」这类现查，同对象目录缓存 / 空 where 第 1 页还在。取消之后 apply 灌了这页，没守住取消前那张浮现表。

契约第 3 条就是修这条：空表、假 kind、取消，都不得按住旧表或倒目录。

## 中游：一句话不是一次 bind

同一句话可以打出不止一张 pending：

- 空 hop 从没有条件的祖先目录第 1 页起探（第 2 条报 0，BF `98af488` 修过起探点，管子还在）。
- BFF 自己 POST /preview 或轮询，和模型那一枪不是同一张表。
- 过审没出令牌之后，模型改打假 kind。假 kind 的空结果被写成 pending。

插件里这些第二次、第三枪不会变成「你看见的那张表」。

## 下游：一张 pending 不是一张表

右表不守「这一次」：

- `shouldRejectEmptyIncomingSheet`：空的**现查**进来，按住旧表。空的**过审**换 kind 不走这条，报销单 0 能上屏。
- `shouldHoldSideKindView`：新 pending 换 kind，按住旧 kind。BG `2d4bbac` 改成「空侧视图不 hold」，空过审更能盖掉 97 行。
- 取消：抽屉关了，表倒成连接器目录（第 4 条取消 → 客户约 20 行）。
- 更早：chrome 跟 pending、tbody 跟另一份 rows（对齐根因）。

所以左 AI = 右表经常不是产品规则里的「同一张」。

## 要修的契约（只这一条，不再追加印证）

1. **只有连着业务表的对象能当预览/写目标。** 口语短名是别名，不是第二张表。没有业务表的图谱概念不得 preview。不写死报销单→费用报销。
2. **一句话只产生一张 pending。** BFF 不得另写一张盖掉闸已经查对的那一次。假 kind 的第二枪不得上屏。过审必须落在已连接那张表的匹配集上，解析偏了不能改打空对象。
3. **右表必须换上这一张。** 空表、假 kind、取消，都不得按住旧表或倒目录。
4. **模糊名对上多家：先选再继续**（五问 §12）。人要的是一批，不要一家家问。
