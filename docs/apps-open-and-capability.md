## 1. 打开：不要在列表页上挤着用

你要的「弹窗、别在原窗口里用」方向对：列表是目录，打开才是应用。

建议再拆一层，否则复杂应用会被对话框卡死：

| 打开什么 | 怎么开 | 为什么 |
|---|---|---|
| 草稿 / 预览 / 要不要采纳 | **对话框** | 看一眼 spec、点采纳或关掉，挡一下没关系 |
| 已激活、要日常用 | **独立工作面**，可撕成**这个应用自己的浮窗** | 浮窗里是这个创建的应用，不是整块「业务应用」。顶栏模块自己的浮窗另算 |
| 改 spec / 版本 | 工作面里的抽屉，或再开一个对话框 | 别和填数据抢同一张表 |

列表页只负责：我有哪些应用、草稿、创建入口。点进去，列表退到后面。

不新增顶栏模块、不新增路由。浮窗是已有桌面能力，不是新页面。

## 2. 删除：草稿和已激活都要能删

现在缺这个，要补。

- **草稿：** 确认后从列表拿掉，没激活就没有用户当真理的数据。
- **已激活：** 必须再确认一次。默认**软删/归档**（列表消失、只读、SQLite 表先留着），避免手滑丢掉台账。勾「连数据一起删」才硬删。
- 两个同名草稿可以分别删，不能当同一个。
- 删除不是写业务系统。本地 SQLite 只动这个应用自己的表。

## 2b. 现网创建流程（2026-09-19）

不要推翻重做。现网就是这条，后半段没接完。

1. 业务应用 → 应用 Tab → 创建应用。
2. 写描述。向导先问本地台账还是邮箱 / 业务 / 文件，不默认铺满 uses。
3. `fde-app-builder` 把话生成 `fde-app/v1` spec。左栏开构建会话。
4. 草稿。打开是对话框：预览 / 采纳并激活 / 删。
5. 采纳后进独立工作面，数据进该应用 SQLite。目录运行中在前，草稿折起。
6. 日常在工作面用。声明了的能力才画。
7. 改字段/版本走建造抽屉（改 spec → 激活修订 → 回滚）。不是再说一句提示词。

创建和改应是同一条：话 → `fde-app-builder` → spec → 工作面。spec 是运行时契约，不是卡死 builder 的框。写不下就扩 spec。现在 spec 太瘦：对象/视图种类有，工作面怎么铺没有；已有应用再用提示词出新修订的入口也没有。

## 3. 创建应用是干什么的（Ace 2026-09-19）

工作台没有的功能，用户用**创建应用**按需求生成一个**真实可用的应用**。标准是 WorkBuddy 能做出的那种完整产品界面，但我们要多两样：数据持久化，以及接上工作台已有能力。

参照（WorkBuddy，只是 HTML，我们要超过它）：

- [健身工作台](/cursor/stores/bc-aea46619-2327-43a7-a094-57e6e76a7d7e/media/workbuddy-fitness-ref.png)：自己的导航、跟练卡片、播放、身体数据记录。工作台没有「运动塑形」模块，也要能生成这种应用。
- [生活工作台·记账](/cursor/stores/bc-aea46619-2327-43a7-a094-57e6e76a7d7e/media/workbuddy-life-ref.png)：自己的栏目（记账/习惯/健身/日程）、概览数字、记一笔、图、流水。刷新后数据还在，不是静态页。

不是同一张后台表换列名。不是一层不能存数据的 HTML。  
接能力：该用 AI / 文件 / 记忆 / 浮窗 / 闸的时候走已有模块，不在页面里假造一套。

Ace 2026-09-19 纠正：用户就是要用提示词**创建和改**应用。创建和改是同一条路：话 → spec → 工作面。没有「能做出来就不能改」的道理。对象、字段、动作、看哪种页、工作面怎么铺、接哪些能力，都从提示词进 spec 再画。现网这些应用是创建应用做的，不是手写进 `src/` 的。决策 3 只禁止为每一句提示词写一套独特代码，**不是**禁止用提示词改应用。半成品在：spec 只接到对象/视图种类，工作面怎么铺还没进 spec，已有应用再用一句提示词改也还没做成跟创建同一条入口。新建说「再密一点」和改已有应用，现在都走不通——是同一条路只接了一半，不是能建不能改。

现网 L1 只有表/表单/看板/统计，**生不出这两张图这种产品**。要达到这个标准，创建必须能按需求铺页面（卡片、栏目、概览、记录），数据进 SQLite，并声明用哪些平台能力。禁止把这两张图做成内置模板。

## 3b. 能生成什么，该复用什么

工作台已有功能不够时，用户用创建应用补洞。不是「说出一个品类就能生成那个软件」。

### 判断标准（用这个，不用品类名单）

用户能说清：**有哪些对象、字段、动作、要看哪几种视图**，并且数据可以住在本机 SQLite（或引用业务系统 id）→ **L1 声明式应用该接住**。  
用户实际要的是**一块专用交互**（画布、收件箱、排课课表、店后台）→ **不要生成假的**。去复用工作台已有模块，或明确本版不做。L2 代码插件仍后置（决策 3）。

### 复用，不翻造

应用通过已定能力接线，不把工作台再实现一遍：

| 工作台已有 | 应用该怎么用 |
|---|---|
| AI 会话 | 创建、问数、跑声明的 `agent` 动作；新开会话要在左栏看得见 |
| 业务记录 / 过账闸 | `ref:biz` 只存 id + 快照；写外部必须预览→确认 |
| 记忆 | 上下文包；重要动作只起草卡片 |
| IM | 拟回放进输入框，人点发送；禁止自动群发 |
| 早报 + MCP | 邮箱、新闻、未完成工作从这里进，应用只做规则和台账 |
| 文件 | 稿、附件、导出走文件模块，应用只留引用 |
| 计划 | 「摘成待办」真落库 |
| 浮窗 | 打开使用的应用可以撕出来并排 |

禁止：在 SQLite 里抄一整个邮箱/ERP；生成一个「看起来像 Gmail/PPT」但不能用的壳。

### 你举的例子，补全后是这样

- **AI 邮件管理：** 收信/账户复用早报 MCP 邮箱。应用只做：规则、待办、标签、要跟进的人、交给 AI 起草。不生成收件箱客户端。
- **AI 教务：** 学生 / 课程 / 成绩 / 请假审批，L1 能做。排课课表、日历视图规格 04 本版不做，不要假装做了。
- **PPT：** L1 做不了幻灯片画布。能做的是大纲台账 + 交给 AI 出稿 + 结果进文件。本版不承诺「生成 PPT 软件」。
- **电商 AI 运营：** 活动、内容日历、对账引用、日报，L1 能做。店后台/平台 API 必须先有连接器；没有连接器就只做本地运营台账，并说清楚。

Builder 生成前要先问清：这是本地台账，还是要接邮箱/业务系统/文件？接就走已有模块，不编一个假接口。

### 复杂度台阶（不要一步登天）

1. **现在该做深的：** 打开方式 + 删除 + 工作面不像脚手架 + 多实体台账 + 动作 + 引用业务对象 + 复用 AI/记忆/闸。
2. **应用声明「我用工作台哪一块」**（邮箱源、业务型、早报区块），仍是 L1。
3. **L2 插件**（真要自定义交互）后置，和决策 3 一致。

「邮件 / 教务 / PPT / 电商」只是例子，禁止写进产品代码当模板名单。
